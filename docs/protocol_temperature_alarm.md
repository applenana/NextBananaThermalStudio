# 香蕉热成像过热/过冷报警接入协议

| 项目 | 内容 |
| --- | --- |
| 文档版本 | 1.0 |
| 协议版本 | 1 |
| 适用固件 | 香蕉热成像固件 v1.7.1 及以上 |
| 最后更新 | 2026-10-19 |

本文档面向需要将自有蜂鸣器、声光报警器、继电器控制器、PLC 网关或上位机接入香蕉热成像温度报警功能的客户。

协议分为两部分：

- 报警事件协议：固定长度 ASCII 行，任何简单 MCU 都可以解析。仅制作报警模块时，只需实现这一部分。
- 配置管理协议：ASCII 命令加单行 JSON 响应，供客户自研上位机读取、修改和持久化热成像设备的报警参数。

> 安全提示：本协议用于测温提示和设备联动，不是经过功能安全认证的紧急停机总线。用于人身安全、消防或危险设备控制时，必须另设独立传感器、硬件联锁和失效保护。

## 1. 接入架构

支持以下三种接入方式。

### 1.1 通过 BananaThermal Studio 转发到客户报警模块（推荐）

```text
热成像设备 ──USB CDC──> BananaThermal Studio ──USB CDC──> 客户报警模块
```

Studio 负责解析热成像数据、显示报警，并把报警事件原样、优先转发到用户选择的第二个串口。客户报警模块只会收到本协议的 `!A` 事件行，不需要理解热成像帧、JSON 或配置命令。

此方式适合使用带 USB Device 功能的简单 MCU 控制蜂鸣器、警灯或继电器。

### 1.2 客户自研上位机直连热成像设备

```text
热成像设备 ──USB CDC──> 客户上位机 ──自定义接口──> 客户业务设备
```

客户上位机需要持续解析 `!A` 事件行；若还要配置报警参数，则同时实现第 6 节中的命令和 JSON 响应。开启热成像或可见光推流后，同一串口还会传输二进制图像帧，解析要求见第 8 节。

### 1.3 带 USB Host 的客户设备直连热成像设备

客户设备可作为 USB Host 独占连接热成像设备，直接接收同一套事件协议。此时 BananaThermal Studio 不参与连接，客户设备自行负责 USB CDC 枚举、配置和状态管理。

## 2. 串口参数

| 项目 | 参数 |
| --- | --- |
| 传输接口 | USB CDC 虚拟串口 |
| 波特率 | 115200 bit/s（USB CDC 中为逻辑配置） |
| 数据位 | 8 |
| 校验位 | 无 |
| 停止位 | 1 |
| 流控 | 无 |
| 字符编码 | ASCII |
| 行结束符 | LF，即 `0x0A`；接收方建议兼容 CRLF |

官方上位机会在 Windows 和 Android 上打开端口后拉高 DTR、RTS。客户自研主机建议采用相同行为，以兼容不同 USB CDC 固件和 USB 转串口实现。

## 3. 报警事件协议（报警模块必须实现）

### 3.1 帧格式

```text
!A,1,<kind>,<state>,<temperature_deci>\n
```

报警行固定为 15 字节（包含末尾 LF），正则表达式为：

```text
^!A,1,[HL],[01],[+-][0-9]{4}\n$
```

字节布局：

| 偏移 | 长度 | 内容 | 说明 |
| ---: | ---: | --- | --- |
| 0 | 2 | `!A` | 报警帧魔数 |
| 2 | 1 | `,` | 分隔符 |
| 3 | 1 | `1` | 协议版本 |
| 4 | 1 | `,` | 分隔符 |
| 5 | 1 | `H` / `L` | 过热 / 过冷通道 |
| 6 | 1 | `,` | 分隔符 |
| 7 | 1 | `1` / `0` | 活动 / 解除 |
| 8 | 1 | `,` | 分隔符 |
| 9 | 5 | `[+-]dddd` | 实测温度，单位 0.1 °C |
| 14 | 1 | `\n` | LF 行结束符 |

字段定义：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| `kind` | `H` | 过热通道，依据当前热成像有效视区的最高温度判断 |
| `kind` | `L` | 过冷通道，依据当前热成像有效视区的最低温度判断 |
| `state` | `1` | 通道已触发；活动期间的重复帧也使用 `1` |
| `state` | `0` | 通道已解除或被用户确认 |
| `temperature_deci` | `[+-][0-9]{4}` | 发送该事件时的实测温度，单位为 0.1 °C |

温度字段必须带正负号并保留四位数字。例如：

- `+0850` 表示 85.0 °C；
- `+0000` 表示 0.0 °C；
- `-0050` 表示 -5.0 °C。

线上的理论表示范围为 -999.9～999.9 °C。设备报警配置范围较窄，详见第 6.4 节。

### 3.2 报文示例

```text
!A,1,H,1,+0850
!A,1,H,0,+0575
!A,1,L,1,-0050
!A,1,L,0,+0025
```

含义依次为：

1. 过热报警触发，最高温度 85.0 °C；
2. 过热报警解除，最高温度 57.5 °C；
3. 过冷报警触发，最低温度 -5.0 °C；
4. 过冷报警解除，最低温度 2.5 °C。

### 3.3 H/L 是两个独立通道

接收方必须分别保存 `H` 和 `L` 的活动状态，不能把每一帧理解成整个报警系统的单一状态。

推荐逻辑：

```text
buzzer_on = high_active OR low_active
```

例如，`H=1`、`L=1` 后只收到 `H=0`，此时 `L` 仍然活动，蜂鸣器不能关闭。只有 H、L 均为 0 时才关闭公共蜂鸣器。

如果客户设备具有两路输出，也可以分别将 H、L 映射为过热和过冷指示灯或继电器。

### 3.4 重复帧是心跳，不是重复触发

活动报警可按配置周期重复上报，默认每 1000 ms 发送一次 `state=1`。重复帧用于：

- 报警模块中途插入后恢复当前活动状态；
- 抵抗偶发丢行；
- 让客户设备监测报警链路是否仍在工作。

收到与当前状态相同的 `state=1` 时，应更新温度和最后接收时间，但不应反复重启蜂鸣器节奏、重复弹窗或重复执行一次性动作。

只有 `state` 发生变化时，才属于新的触发或解除事件。

### 3.5 无应用层 CRC

v1 事件帧不包含 CRC。USB CDC 已提供底层差错检测，固定魔数、固定长度、固定分隔符和有限字段值用于拒绝错误数据。

如果客户需要把事件继续转发到 RS-485、无线电或其他易受干扰的链路，建议在外层增加 CRC、序号和应答，不要修改 `!A` 帧本身，以保持兼容。

## 4. 报警模块最小处理逻辑

报警模块应满足以下要求：

1. 按 LF 收取一行，允许忽略行内的 CR；
2. 仅接受完全符合 v1 固定格式的 15 字节事件帧；
3. 分别维护 H、L 两个布尔状态；
4. 重复活动帧只刷新温度和心跳时间；
5. 不能因收到一个通道的解除帧而清除另一个通道；
6. 未知版本、未知类型、非法状态、错误符号、非数字温度或超长行必须直接忽略；
7. 上电后将 H、L 初始化为 0；
8. 不需要向 Studio 返回 ACK，也不应向该串口周期发送调试文本。

### 4.1 可移植 C 解析示例

以下代码以“已去除末尾 CR/LF 的一行”为输入：

```c
#include <stdbool.h>
#include <stddef.h>
#include <stdint.h>

typedef struct {
    bool high_active;
    bool low_active;
    int16_t high_deci_c;
    int16_t low_deci_c;
} AlarmState;

static bool is_digit(char value) {
    return value >= '0' && value <= '9';
}

bool alarm_parse_line(const char *line, size_t length, AlarmState *state) {
    if (line == NULL || state == NULL || length != 14) return false;

    if (line[0] != '!' || line[1] != 'A' || line[2] != ',' ||
        line[3] != '1' || line[4] != ',' || line[6] != ',' ||
        line[8] != ',') {
        return false;
    }

    const char kind = line[5];
    const char active = line[7];
    const char sign = line[9];
    if ((kind != 'H' && kind != 'L') ||
        (active != '0' && active != '1') ||
        (sign != '+' && sign != '-')) {
        return false;
    }

    for (size_t i = 10; i <= 13; ++i) {
        if (!is_digit(line[i])) return false;
    }

    int16_t temperature = (int16_t)(
        (line[10] - '0') * 1000 +
        (line[11] - '0') * 100 +
        (line[12] - '0') * 10 +
        (line[13] - '0'));
    if (sign == '-') temperature = (int16_t)-temperature;

    if (kind == 'H') {
        state->high_active = active == '1';
        state->high_deci_c = temperature;
    } else {
        state->low_active = active == '1';
        state->low_deci_c = temperature;
    }
    return true;
}

void alarm_apply_outputs(const AlarmState *state) {
    const bool any_active = state->high_active || state->low_active;
    set_buzzer(any_active);
    set_overheat_indicator(state->high_active);
    set_overcool_indicator(state->low_active);
}
```

串口接收层建议使用 32 字节以内的小缓冲区。遇到 LF 时调用解析函数；遇到超长行时丢弃整行，直到下一个 LF 再恢复，避免缓冲区溢出。

## 5. 热插拔、断线与安全策略

### 5.1 经 Studio 连接报警模块

Studio 成功打开客户报警模块串口后，会立即发送两条状态快照，顺序为 H、L。即使当前没有报警，也会发送两个 `state=0` 帧，使模块状态确定。

当热成像设备正常断开，或用户主动断开报警模块时，Studio 会尝试先发送 H、L 两个解除帧，再关闭报警模块串口。Android 端还会为异步 USB 写入预留短暂发送时间。

物理拔线、主机掉电或进程崩溃时无法保证解除帧送达。因此客户必须根据风险等级选择断线策略。

### 5.2 推荐断线策略

- 普通提示设备：通信超时后关闭蜂鸣器，同时点亮“通信故障”指示灯；
- 安全敏感设备：通信超时后保持原报警，或切换为不同节奏的故障报警，等待人工确认；
- 自动控制设备：通信超时进入预先定义的安全状态，不得把“无数据”当成“温度安全”。

只有在客户上位机固定配置了 `repeat_ms` 时，才建议用报警心跳做超时判断。例如 `repeat_ms=1000` 时，可将 3.5 秒未收到当前活动通道的重复帧判定为链路异常。

若允许用户把 `repeat_ms` 设置为 0 或 60000 ms，报警模块就不能使用固定的短超时自动清除状态。

## 6. 配置管理协议（客户自研上位机选配）

报警模块本身不需要实现本节。所有命令均为 ASCII 单行命令，以 LF 结束；设备也使用 LF 结束响应。设备接受 CRLF，单条命令不得超过 255 个字符。

### 6.1 命令列表

```text
alarm get
alarm ack
alarm defaults
alarm set <master> <high_enabled> <high_c> <low_enabled> <low_c> <high_hyst_c> <low_hyst_c> <trigger_ms> <clear_ms> <latched> <repeat_ms>
```

命令说明：

| 命令 | 作用 |
| --- | --- |
| `alarm get` | 读取完整配置和 H/L 当前活动状态 |
| `alarm ack` | 确认并解除当前 H/L 报警；配置不变 |
| `alarm defaults` | 恢复默认配置并写入设备存储 |
| `alarm set ...` | 整体替换报警配置并写入设备存储 |

配置必须整体写入，v1 不支持只修改单个字段。

### 6.2 `alarm set` 参数

| 参数 | 类型 | 含义 |
| --- | --- | --- |
| `master` | `0` / `1` | 报警总开关 |
| `high_enabled` | `0` / `1` | 过热报警开关 |
| `high_c` | 浮点数 | 过热门槛，°C |
| `low_enabled` | `0` / `1` | 过冷报警开关 |
| `low_c` | 浮点数 | 过冷门槛，°C |
| `high_hyst_c` | 浮点数 | 过热恢复迟滞，°C |
| `low_hyst_c` | 浮点数 | 过冷恢复迟滞，°C |
| `trigger_ms` | 无符号整数 | 越界持续多久后触发 |
| `clear_ms` | 无符号整数 | 进入恢复区持续多久后解除 |
| `latched` | `0` / `1` | 是否锁存报警 |
| `repeat_ms` | 无符号整数 | 活动报警重复上报周期；0 表示关闭 |

示例：

```text
alarm set 1 1 60.0 1 0.0 2.0 2.0 500 1000 0 1000
```

该配置表示：打开总开关；过热 60.0 °C；过冷 0.0 °C；冷热迟滞均为 2.0 °C；越界持续 500 ms 后触发；进入恢复区持续 1000 ms 后解除；不锁存；活动报警每 1000 ms 重发。

### 6.3 默认值

| 参数 | 默认值 |
| --- | ---: |
| 报警总开关 | 关闭 |
| 过热报警 | 关闭 |
| 过热门槛 | 60.0 °C |
| 过冷报警 | 关闭 |
| 过冷门槛 | 0.0 °C |
| 过热迟滞 | 2.0 °C |
| 过冷迟滞 | 2.0 °C |
| 触发确认时间 | 500 ms |
| 恢复确认时间 | 1000 ms |
| 锁存 | 关闭 |
| 活动重复上报 | 1000 ms |

恢复默认会关闭总开关及两个报警分项，不会立即启用报警。

### 6.4 参数约束

| 参数 | 合法范围 |
| --- | --- |
| `high_c` | -39.0～300.0 °C |
| `low_c` | -40.0～299.0 °C |
| 门槛关系 | `low_c < high_c` |
| `high_hyst_c` / `low_hyst_c` | 0.1～20.0 °C |
| `trigger_ms` / `clear_ms` | 0～10000 ms |
| `repeat_ms` | 0，或 250～60000 ms |
| 所有布尔参数 | 仅接受 0 或 1 |

官方上位机按 0.1 °C 输出门槛和迟滞。第三方实现也应采用相同精度，以避免写入后的回读值与本地显示不一致。

### 6.5 成功响应

成功响应是一行 JSON：

```json
{"type":"temperature_alarm","version":1,"ok":true,"operation":"set","persisted":true,"master":true,"highEnabled":true,"highThreshold":60.0,"lowEnabled":true,"lowThreshold":0.0,"highHysteresis":2.0,"lowHysteresis":2.0,"triggerDelayMs":500,"clearDelayMs":1000,"latched":false,"repeatMs":1000,"highActive":false,"lowActive":false}
```

字段说明：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `type` | string | 固定为 `temperature_alarm` |
| `version` | integer | 固定为 1 |
| `ok` | boolean | 命令是否被识别并通过参数校验 |
| `operation` | string | `get`、`set`、`ack` 或 `defaults` |
| `persisted` | boolean | 配置是否已可靠保存在设备中 |
| `master` | boolean | 报警总开关 |
| `highEnabled` / `lowEnabled` | boolean | 过热/过冷分项开关 |
| `highThreshold` / `lowThreshold` | number | 过热/过冷门槛，°C |
| `highHysteresis` / `lowHysteresis` | number | 过热/过冷迟滞，°C |
| `triggerDelayMs` | integer | 触发确认时间，ms |
| `clearDelayMs` | integer | 恢复确认时间，ms |
| `latched` | boolean | 是否锁存 |
| `repeatMs` | integer | 活动重复上报周期，ms |
| `highActive` / `lowActive` | boolean | 当前 H/L 活动状态 |

`alarm set` 和 `alarm defaults` 返回 `ok=true` 但 `persisted=false` 时，表示参数已通过校验并应用到本次运行，但写入设备文件系统失败。客户上位机必须明确提示“未持久化”，不能向用户报告保存成功。

### 6.6 失败响应

参数数量、格式或范围非法时返回：

```json
{"type":"temperature_alarm","version":1,"ok":false,"operation":"set","error":"invalid parameters"}
```

失败后原有配置保持不变。

### 6.7 命令响应期间仍要处理事件

`alarm ack`、`alarm set` 或 `alarm defaults` 可能导致活动通道立即解除。设备会先输出一条或两条 `!A,...,0,...` 事件行，再输出 JSON 响应。

因此客户上位机等待配置响应时，不能假设下一行必然是 JSON。正确做法是：

1. 每行先尝试解析 `!A` 事件；
2. 再尝试解析 `type=temperature_alarm` 的 JSON；
3. 其他日志或协议数据交给对应解析器；
4. 建议命令响应超时设置为 2500 ms，并且同一时间只发送一条配置命令。

## 7. 报警状态机语义

### 7.1 过热通道

- 触发条件：每帧最高温度 `>= high_c`，并连续满足 `trigger_ms`；
- 恢复区：每帧最高温度 `<= high_c - high_hyst_c`；
- 自动解除：连续处于恢复区 `clear_ms`，且 `latched=0`。

例如 `high_c=60.0`、`high_hyst_c=2.0`：

- 60.0 °C 及以上属于过热越界；
- 58.0 °C 及以下才进入恢复区；
- 58.0～60.0 °C 是迟滞区，已触发的报警保持活动，未触发的报警不会触发。

### 7.2 过冷通道

- 触发条件：每帧最低温度 `<= low_c`，并连续满足 `trigger_ms`；
- 恢复区：每帧最低温度 `>= low_c + low_hyst_c`；
- 自动解除：连续处于恢复区 `clear_ms`，且 `latched=0`。

例如 `low_c=0.0`、`low_hyst_c=2.0`：

- 0.0 °C 及以下属于过冷越界；
- 2.0 °C 及以上才进入恢复区；
- 0.0～2.0 °C 是迟滞区。

### 7.3 确认和锁存

- `latched=1` 时，温度恢复后报警仍保持活动，必须执行 `alarm ack` 或在设备菜单中确认；
- `alarm ack` 会立即清除当前 H/L 活动状态并发出解除事件；
- 如果确认时温度仍未回到迟滞恢复区，该通道会保持“已确认、静音”状态，不会立即重新触发；
- 温度至少回到一次恢复区后，通道才会重新布防。

### 7.4 数据无效时的行为

报警依据设备当前校准曲线修正后的温度。过热使用当前有效热成像视区的最高温，过冷使用最低温，不使用中心点温度。

传感器未就绪、温度非有限数、最高/最低关系非法或数据超出合理范围时：

- 不会触发新报警；
- 未完成的触发/恢复计时会被取消；
- 已活动报警不会因“数据无效”而自动解除。

接收方同样不得把链路中断或无数据解释为温度已经恢复。

## 8. 与热成像、可见光和图库协议共存

报警具有最高发送优先级，但设备不会把报警行插入一张已经开始发送的二进制热成像帧或可见光帧内部。报警会在当前完整记录结束后、下一帧开始前抢占串口。

客户上位机直连热成像设备时应遵守以下规则：

- 正在读取 `BEGIN...END` 热成像帧或 `VBEG...VEND` 可见光帧时，必须按对应帧长度完成读取，不要在二进制载荷内部搜索 `!A`；
- 位于帧边界的独立 ASCII 行才按本协议解析；
- 图库下载使用逐行十六进制文本，报警只会插入在完整记录行之间；
- 图库解析器应忽略非十六进制的 `!A` 行，同时把它交给报警解析器处理。

经 Studio 转发到客户报警模块时，Studio 已完成上述多协议解析，模块端不会收到二进制热帧。

## 9. 推荐接入流程

### 9.1 仅接入客户报警模块

1. MCU 实现 USB CDC Device；
2. 主机端选择该虚拟串口并以 115200、8N1 打开；
3. MCU 按 LF 分行，严格解析 15 字节 `!A` 帧；
4. 分别维护 H/L 状态并驱动输出；
5. 验证模块中途插入时能正确处理 Studio 发送的 H/L 状态快照；
6. 验证重复活动帧不会重复启动一次性动作；
7. 验证只解除一个通道时另一个通道仍保持报警；
8. 根据产品风险定义掉线、主机崩溃和模块复位行为。

### 9.2 客户自研上位机完整接入

1. 打开热成像 USB CDC，并持续运行多协议解析器；
2. 连接成功后发送 `alarm get`；
3. 校验 JSON 中的 `type`、`version`、`ok` 和所有字段类型；
4. 始终优先处理 `!A` 事件，更新 UI、声音和外部联动；
5. 修改配置时发送完整 `alarm set`，以设备回读为最终状态；
6. `persisted=false` 时提示存储失败；
7. 用户确认报警时发送 `alarm ack`，不要只在本地关闭提示；
8. 设备断开时进入“数据不可用/通信故障”状态，不要显示为“无报警”。

## 10. 验收测试向量

接收方至少应通过以下测试：

| 输入 | 预期结果 |
| --- | --- |
| `!A,1,H,1,+0850\n` | H=活动，温度 85.0 °C |
| 再次输入同一行 | 状态不重复切换，只刷新心跳 |
| `!A,1,L,1,-0050\n` | H、L 同时活动 |
| `!A,1,H,0,+0575\n` | 仅解除 H，L 仍活动 |
| `!A,1,L,0,+0025\n` | H、L 均解除 |
| `!A,2,H,1,+0850\n` | 未知版本，忽略 |
| `!A,1,X,1,+0850\n` | 未知类型，忽略 |
| `!A,1,H,2,+0850\n` | 非法状态，忽略 |
| `!A,1,H,1,0850\n` | 缺少符号，忽略 |
| `!A,1,H,1,+85.0\n` | 非固定整数格式，忽略 |
| 超长行后接合法帧 | 丢弃超长行，并能在下一个 LF 后恢复 |
| 模块在 H 活动时连接 Studio | 收到 H 活动快照和 L 当前快照 |
| 热成像正常断开 | Studio 尝试发送 H/L 解除帧 |

## 11. 兼容性要求

- 接收方必须检查协议版本，不得把未知版本按 v1 强行解析；
- v1 字段顺序和固定宽度不会在同一版本内改变；
- 客户模块应忽略无法识别的行，为后续协议扩展保留兼容空间；
- 若未来需要增加设备编号、序号、CRC 或更多报警类型，将使用新版本或不同魔数，不会静默改变 v1 语义。

第三方接入联调时，建议同时提供：客户设备型号、USB 串口芯片或 MCU、目标平台、报警输出方式、是否经过 Studio 转发，以及上述验收测试结果。
